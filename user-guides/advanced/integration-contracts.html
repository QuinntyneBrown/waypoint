Integration contracts

This page is for the people who run Waypoint and the people who connect something to it — not for youth, mentors or guardians. It documents the way command line, the HTTP surface and how it authenticates, the realtime hub, the headers on every response, and what happens during maintenance. If you are here to use the product, every other page in this guide is a better starting point.

Program Administrator W-UG-20

What this page is, and what it is not

Waypoint ships two things an operator can talk to directly: an HTTP API, and a command-line tool called way.

The way command line is operational tooling, not a product feature

It exists so an operator can bring up a database, create the first administrator, and run bulk or recovery work from a terminal. It is not part of anybody's day-to-day job, it has no place in a training session, and nothing in it is required to use Waypoint normally. If you are not the person who deploys Waypoint, you will never need it.

Both surfaces run the same application code. The command line sends the same commands through the same validation and the same audit logging as the API does, so there is no back door that skips a rule.

Not approved for production. Waypoint is a development project. No independent security, privacy, safeguarding, or accessibility review has been completed, and no release is approved for production use or for storing real participant information. Use synthetic data only.

The way command line

Installing and getting help

way is packed as a .NET tool. Install it, then ask it what it can do: 

way --help

Every group and every command answers --help as well, and that answer is authoritative for typed arguments and options: 

way db --help
way invite create --help

--help and --version are handled before anything else starts up, so they work without any configuration at all.

Required configuration

Every other command needs the same configuration the API needs. Set these through the host environment or another standard .NET configuration provider, and never commit their values.

Variable What it is
DOTNET_ENVIRONMENT Set to Production for a real deployment. This is what turns on the startup checks described at the foot of this page.
ConnectionStrings__Default The durable SQL Server connection string.
Jwt__Issuer Token issuer, matched on validation.
Jwt__Audience Token audience, matched on validation.
Jwt__SigningKey Signing key for access tokens.
Jwt__AccessTokenMinutes Access token lifetime in minutes.
AuditIntegrity__SigningKey Signing key for the audit chain. Change it and the integrity check on the audit log will fail.
SensitiveData__EncryptionKey Encryption key for sensitive stored columns.

All three signing and encryption keys must contain at least 32 characters and must not still carry the checked-in placeholder prefix.

Who the command acts as

Waypoint audits by person, not by process, so every command that changes something is attributed to a real Program Administrator account. By default way picks the oldest active Program Administrator. The global option --actor chooses one deterministically: 

way --actor 0f2c9d24-6a1b-4f0e-9d33-6c0a2f5b8e41 user list

It fails in exactly two ways, and both are worth recognising.

error: No active Program Administrator is available; run 'way db seed' first.

You did not pass --actor and the database has no active Program Administrator to fall back on. This is what a fresh database looks like.

error: The selected actor is not an active Program Administrator.

You passed --actor, but that identifier is not a Program Administrator, or the account is not Active.

The two db bootstrap commands (migrate and seed) and db reset do not need an actor, because they may have to run before any account exists. Everything else does.

db — database lifecycle

Manage the Waypoint database schema and seed data.

Command What it does Options
db migrate Applies all pending database migrations. None.
db seed Migrates, then creates an initial Program Administrator if one with that email does not already exist. Safe to re-run: an existing account is printed back unchanged. --email, --password, --display-name — all required.
db reset Deletes and recreates the configured database. --confirm — required.

Bring a new environment up in two commands:

way db migrate
way db seed --email director@example.org --password "…" --display-name "Program Director"

db seed prints the account as JSON. That is the first and only account in the system — development starts with an empty database and creates no demo accounts. Everyone else arrives by invitation.

way db reset destroys the database

It drops and recreates the database named in ConnectionStrings__Default. Every account, every submission, every attendance record and the entire audit log are gone, and nothing in Waypoint can bring them back. It exists for throwaway development databases. The confirmation must be the exact string RESET, and anything else is refused with error: Database reset requires --confirm RESET. Read the connection string before you press return. 

way db reset --confirm RESET

user — accounts

Manage Waypoint user accounts.

Command What it does Options and arguments
user create Creates an active user account directly, without an invitation. --email, --password, --display-name, --role required; --cohort, --mentor optional.
user list Lists non-removed users as JSON. --role to filter, --search to match email or display name.
user set-role Changes a user's role and revokes their existing sessions, so the new role takes effect on next sign-in rather than whenever their token happens to expire. Arguments: user id, then the canonical role name.
user reset-password Emails the user a single-use password reset link. Argument: user id.
user deactivate Deactivates a user and revokes existing sessions. Argument: user id.

--role takes a canonical stored role name — Youth, Mentor, ProgramAdministrator, Guardian or Volunteer — not a display label. 

way user list --role Mentor --search rivera

There is no user remove. Permanent removal runs through the privacy request workflow with its two-person rule — see Privacy, consent and the audit trail.

invite — invitations

Manage account invitations.

Command What it does Options and arguments
invite create Creates and emails an invitation. --email, --role required; --cohort, --mentor optional.
invite resend Replaces the invitation's token and emails it again. The old link stops working. Argument: invitation id.
invite revoke Revokes a pending invitation. Argument: invitation id.
invite list Lists invitations as JSON, deliberately without exposing token hashes. None. 
way invite create --email new.mentor@example.org --role Mentor

Invitations expire after 14 days and are single use, whether they were created here or from the Invitations screen.

cohort — cohorts and placements

Command What it does Options and arguments
cohort create Creates a cohort. --name, --track, --lead-mentor required; --start, --end, --location optional.
cohort assign-mentor Sets the lead and supporting mentors for a cohort. Argument: cohort id. --lead required; --supporting takes several ids.
cohort add-youth Places a youth in a cohort. Arguments: cohort id, then youth user id.
cohort progress Prints the cohort progress board as JSON. Argument: cohort id. --track optional.

--track on cohort create must name a published track. Draft and in-review curriculum cannot be assigned. 

way cohort progress 6b1e4a90-7c2d-4b53-90f1-2ad8c3e77b04

import — roster CSV

Command What it does Options
import youth Imports a youth roster CSV. Unlike the in-product import, this commits directly — there is no preview step. --from — required, must exist.

The file's header row must use these exact column names: Name, Email, Cohort, Mentor, Track, Status and Consent. Matching ignores letter case. 

way import youth --from ./roster-autumn.csv

report — exports

Command What it does Options and arguments
report youth Exports a youth report and writes it to disk. Argument: youth id. --format required, either pdf or csv; --out optional.
report cohort Exports a cohort report and writes it to disk. Argument: cohort id. --format required, either pdf or csv; --out optional.

With no --out, the file is written into the current directory under the name the server chose, and the full path is printed. Existing files are never overwritten — the command stops with error: Output file already exists: … 

way report cohort 6b1e4a90-7c2d-4b53-90f1-2ad8c3e77b04 --format csv --out ./autumn.csv

badge — manual awards

Command What it does Arguments
badge award Awards a manual badge to an active youth. Automatic badges are earned by the rules attached to them and are not awarded here. Youth user id, then badge id.

token — access tokens

Command What it does Options
token issue Issues a short-lived API access token for an active user and writes an audit entry recording that it did. --user — required, the user's email. 
way token issue --user director@example.org

This is how you get a bearer token for a script or a curl call without going through the sign-in screen. It is audited precisely because it lets one person act as another, so use it sparingly and expect to be asked about it.

Exit codes and error output

Code Meaning
0 Success.
2 A validation failure, an application rule refusing the request, a configuration problem, or a file input/output failure. These are your fault and the message tells you what to fix.
1 Anything else. The message is deliberately terse — error: operation failed (…) naming only the exception type — so that nothing sensitive leaks into a terminal or a build log.

All errors are written to standard error, and every one of them is prefixed error: . Normal output — JSON payloads, written file paths, and the plain confirmations Database migrations applied., Database reset completed. and Completed. — goes to standard output. That split means you can pipe results into another tool and still see failures.

The HTTP surface

Authentication

Every protected endpoint expects a bearer JWT in the standard Authorization header. Get one by signing in at POST /api/auth/sign-in, or by issuing one with way token issue.

Access token — 60 minutes

Short-lived and self-contained. It carries the account's role and a session version; changing someone's role or deactivating them advances that version and invalidates every token they hold.

Refresh token — 30 days, rotating

Presented to POST /api/auth/refresh and rotated on every use: each refresh returns a new refresh token and retires the old one.

Reuse detection

Presenting a refresh token that has already been rotated, or one that was revoked, is treated as a compromise rather than a mistake. The whole token family is revoked and the session ends. A client that stores refresh tokens must therefore never retry a refresh with the old value.

An unauthenticated or no-longer-valid request gets 401 with Your session is no longer valid. Please sign in again. A request that is authenticated but not permitted gets 403, and that denial is itself written to the audit log.

Browsing and probing the API

Locally the API listens on http://127.0.0.1:5211. Three paths are worth knowing:

/swagger

Interactive API documentation covering every endpoint, its parameters and its response shape. It is a development tool and is served under a deliberately relaxed content-security policy so that it can run its own scripts; the API's own JSON responses keep the strict policy.

/health

Liveness. Answers as long as the process is up, and runs no dependency checks at all. This is the one path maintenance mode does not intercept.

/health/ready

Readiness. Answers only when dependencies, including the database, are reachable. Point your load balancer here, not at /health.

Realtime updates

Waypoint pushes a small number of live updates over a SignalR hub at /hubs/realtime.

Connecting

The hub requires the same bearer JWT as the API. A browser websocket cannot send an Authorization header, so the token is passed as an access_token query parameter instead — and that is accepted for paths under /hubs and nowhere else. The rest of the API ignores the query parameter entirely.

A connection is refused, and immediately aborted, unless the token is unexpired and its subject is an active, non-anonymised account whose current role and session version still match the token. The connection is also closed when the token expires rather than being allowed to run on.

The hub is receive-only

There are no client-callable methods. You connect, you listen, and that is the entire contract. Anything that changes state goes through the HTTP API.

The three events

Event Sent to Payload fields
message The recipient of a direct message. id, senderId, recipientId, body, sentAt, readAt
notification The person the notification belongs to. id, eventKey, title, body, linkPath, createdAt
progressChanged Program Administrators, when a youth completes a lesson or saves coding progress. cohortId, youthId

Note what progressChanged does not carry: no names, no scores, no content. It is a signal to refresh the progress board, not a data feed.

Notification event keys

The eventKey on a notification is one of five values, and it is the same key a person can switch off under their notification preferences.

Key Raised when
mentor-messages A message arrives in a mentor thread.
work-graded A mentor grades submitted work.
approval-needed Something is waiting on a staff decision.
badge-earned A badge is awarded, automatically or by hand.
at-risk-alert An at-risk flag is raised.

Events follow the commit, never precede it

Every event is dispatched after the database change it describes has been committed. You will never receive a message for a message that was rolled back, or a progressChanged for progress that did not save.

The reverse guarantee is not offered. Dispatch is best-effort: if the push fails, the underlying change still stands. Treat the hub as a hint to refresh, and treat the API as the source of truth. A client that only listens and never re-fetches will eventually drift.

Recipients are re-checked at dispatch time, not at connection time. If someone's role changed, their session was invalidated or their account was deactivated or removed since they connected, their connection is dropped instead of being sent the event.

What every response carries

X-Correlation-ID

Every single response carries an X-Correlation-ID header. The same value is put into the server's log scope for that request, and on a 500 it is returned in the body as correlationId and shown to the person on screen.

This is the one piece of information that makes a bug report actionable. "It broke this morning" cannot be traced; a correlation identifier goes straight to the log line for that exact request, with its method and route. If you are reporting a problem, quote it. If you are building a client, log it alongside every failed call.

You may supply your own value in the request header and it will be echoed back, provided it is at most 128 characters and contains only letters, digits, hyphens, underscores and dots. Anything else is discarded and replaced with a generated identifier — a deliberate defence against header injection.

Security headers

Header Value
Content-Security-Policy default-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'self' on API responses. The Swagger UI gets a relaxed policy so it can run.
X-Frame-Options DENY
X-Content-Type-Options nosniff
Referrer-Policy no-referrer
Strict-Transport-Security max-age=31536000; includeSubDomains

These headers are attached first, so they ride on every response — including the global 500 handler and the maintenance 503.

X-Waypoint-State

A response can carry X-Waypoint-State to tell a client why it was refused, so the client can route to the right screen rather than showing a generic error. Two values exist: consent-required and media-consent-required. The portal uses them to send a youth to A guardian needs to sign off instead of to a dead end. The header is explicitly exposed through CORS, so a browser client can read it.

Maintenance mode

Maintenance mode is a configuration switch: Maintenance:Enabled set to true. There is no button for it in the product, which is deliberate — it is an operator action taken before a deployment, not a feature.

While it is on, every request except /health is short-circuited with 503 and the header Retry-After: 120. The body is JSON: 

{
  "title": "Waypoint is down for scheduled maintenance.",
  "detail": "Nothing you've done is lost. Please check again shortly.",
  "retryAfterSeconds": 120
}

Nothing gets through: not the API, not the realtime hub, not /health/ready. Only the liveness probe answers, so your orchestrator can still tell the process is alive while it is refusing work.

A person using the portal sees a state page rather than that JSON. It is headed We’ll be right back under the eyebrow Scheduled maintenance, with the line Waypoint is down for a short bit of maintenance. Nothing you’ve done is lost — please check again shortly.

Production startup refuses bad configuration

When the environment is Production, both the API and way validate their configuration before doing anything, and refuse to start if it is unsafe. The command line prints the reason prefixed error: and exits with code 2.

  • No in-memory database. A missing connection string, or the literal value InMemory, is rejected: production requires a durable SQL Server connection string.
  • No placeholder secrets. Jwt:SigningKey, AuditIntegrity:SigningKey and SensitiveData:EncryptionKey must each be at least 32 characters and must not still begin with the checked-in placeholder text.
  • HTTPS application URLs only. The portal and public-site base URLs must be absolute https:// URLs with no embedded credentials.
  • Working, encrypted email. SMTP must be enabled with a host and a from-address, and must use SSL or STARTTLS. A username without a password, or the reverse, is rejected as a misconfiguration.

These checks are why a production deployment fails fast with a clear message instead of starting up and quietly losing invitation emails or writing an audit chain nobody can verify.
