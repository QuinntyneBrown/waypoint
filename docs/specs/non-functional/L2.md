# L2 — Non-Functional & Quality (NFR)

Each L2 traces to an L1 in `non-functional/L1.md`. These cross-cutting requirements are referenced by functional L2s across every subsystem.

## L2-NFR-001: Input validation and injection defense
**Traces to:** L1-NFR-001

All input must be validated and all output encoded to prevent injection and XSS.

**Acceptance Criteria:**
1. Given any request, when processed, then all inputs are validated server-side against a schema (type, length, range, format) and rejected with structured errors on violation.
2. Given user-supplied text is rendered, when output, then it is contextually encoded so stored/reflected XSS is not possible.
3. Given database access, when performed, then queries are parameterized (no string-concatenated SQL) so injection is not possible.
4. Given file uploads (photos, screenshots, CSVs, media), when accepted, then type, size, and content are validated and files are stored/served without executable/script exposure.

## L2-NFR-002: CSRF, CORS, security headers, and rate limiting
**Traces to:** L1-NFR-001

The API must protect against cross-site attacks, set appropriate headers, and rate-limit sensitive endpoints.

**Acceptance Criteria:**
1. Given state-changing requests, when made from a browser, then CSRF protection appropriate to the auth scheme is enforced.
2. Given CORS, when configured, then only approved production web origin(s) are allowed; non-production origins are governed by a separate configured policy.
3. Given any response, when returned, then security headers (Content-Security-Policy, X-Frame-Options/frame-ancestors, X-Content-Type-Options, Referrer-Policy, HSTS) are present.
4. Given sensitive endpoints (sign-in, reset, invite), when called, then they are rate-limited (see L2-AUTH-001).

---

## L2-NFR-003: PII protection and data-subject rights
**Traces to:** L1-NFR-002

The system must protect PII and honour access/correction/withdrawal/retention.

**Acceptance Criteria:**
1. Given personal data, when stored, then it is limited to what is needed, access is restricted to staff and the assigned mentor, and sensitive fields are protected at rest.
2. Given a data-subject request (access/correction/removal or consent withdrawal), when made, then the system supports fulfilling it and records the action (see L2-CONSENT-001).
3. Given retention policy, when data exceeds its needed lifetime, then it can be removed/anonymized while preserving de-identified reporting aggregates.
4. Given logs/telemetry, when emitted, then secrets and sensitive PII are redacted (see L2-NFR-011).

---

## L2-NFR-004: Offline attendance queue and sync integrity
**Traces to:** L1-NFR-003

Offline attendance writes must queue and sync without loss or duplication.

**Acceptance Criteria:**
1. Given an offline attendance write, when created, then it is persisted locally with enough context to replay it on reconnect.
2. Given reconnection, when sync runs, then each queued attendance write is applied exactly once (idempotency keys) so retries never duplicate records.
3. Given a queued attendance write conflicts with a server change, when synced, then conflict resolution is deterministic and the user is informed if their change could not be applied (see L2-NFR-006).
4. Given a shared/borrowed device, when offline attendance writes exist, then they remain private and only sync after the owner is signed in and connected.

---

## L2-NFR-005: Near-real-time notification and message delivery
**Traces to:** L1-NFR-004

The system must deliver notifications and messages to authorized, correctly-scoped recipients in near-real-time.

**Acceptance Criteria:**
1. Given a notification or message, when it is created, then it is delivered to the relevant user/cohort/role groups only.
2. Given a client connects to the delivery hub, when connecting, then it must present a valid token and is added only to groups its identity authorizes (user/cohort/role — see L2-AUTH-010).
3. Given a dropped connection, when it reconnects, then it resumes without missing state (reconciles via reload/fetch) and without duplicate handling.
4. Given a notification or message payload, when sent, then it contains no data the recipient is not authorized to see.

---

## L2-NFR-006: Concurrency and data integrity
**Traces to:** L1-NFR-009

Mutable aggregates must use optimistic concurrency to prevent lost updates.

**Acceptance Criteria:**
1. Given two users edit the same attendance/submission concurrently, when the second saves against a stale version, then the save is rejected with a conflict and the user can reconcile (no silent overwrite).
2. Given a save succeeds, when persisted, then the version token advances.
3. Given a critical multi-step operation (e.g., approve application → create user + enrollment), when performed, then it is transactional (all-or-nothing).

---

## L2-NFR-007: Unsaved-changes protection
**Traces to:** L1-NFR-009

The UI must warn before discarding unsaved changes.

**Acceptance Criteria:**
1. Given a form/page with unsaved changes (reflection, attendance, grading, editors), when the user navigates away or closes, then they are warned and offered to save a draft or cancel.
2. Given a draft is saved, when the user returns, then the draft is restored.

---

## L2-NFR-008: Performance targets
**Traces to:** L1-NFR-005

The system must meet response-time and throughput targets, including on low-powered devices.

**Acceptance Criteria:**
1. Given typical read endpoints under expected load, when called, then the server responds within 300 ms at the median and 800 ms at the 95th percentile (excluding network).
2. Given list/board/report views, when loaded, then they use server-side paging/aggregation so payloads stay bounded regardless of org size.
3. Given a shared Chromebook, when a primary youth screen loads on a throttled connection/CPU, then it reaches interactive within a defined budget (e.g., ≤ 3 s on a mid-tier device) and avoids blocking the main thread.
4. Given concurrent users across all cohorts, when active, then the system sustains the target throughput without error-rate increase.

---

## L2-NFR-009: Responsive layout across breakpoints
**Traces to:** L1-NFR-006

Every UI must render usably from XS to XL.

**Acceptance Criteria:**
1. Given viewport width < 576px, when any app page renders, then layouts are single-column/mobile-first (youth/guardian/volunteer) and no element causes horizontal page overflow.
2. Given wide data (tables, progress matrix, calendar), when rendered on small screens, then it scrolls horizontally within its own container while the page body does not.
3. Given ≥768px and ≥992px and ≥1200px, when staff pages render, then multi-column/dashboard layouts adapt appropriately.
4. Given data tables on XS, when rendered, then they reflow to card rows with labelled cells.

---

## L2-NFR-010: Accessibility (WCAG 2.1 AA)
**Traces to:** L1-NFR-007

The UI must be operable and perceivable per WCAG 2.1 AA.

**Acceptance Criteria:**
1. Given interactive controls, when rendered, then tap targets are ≥44px, every input has a real associated label, and icon-only buttons have accessible names.
2. Given status/state, when conveyed, then it never relies on colour alone (icon/dot + text accompany colour).
3. Given keyboard-only use, when navigating, then all functionality is operable, focus order is logical, and visible focus is shown.
4. Given a dialog opens, when shown, then focus is trapped within it, Escape closes it, and focus returns to the trigger on close.
5. Given text/background, when rendered, then contrast meets AA (and the high-contrast preference exceeds it — see L2-PLATFORM-004).

---

## L2-NFR-011: Observability and operations
**Traces to:** L1-NFR-008

The system must expose health checks, structured logging, and an admin CLI (operational tooling — an out-of-band ops interface, not product scope).

**Acceptance Criteria:**
1. Given a liveness probe (`/health`) and readiness probe (`/health/ready`), when called, then they report process and dependency (DB) health respectively.
2. Given requests, when handled, then structured logs are emitted with correlation ids and secrets/PII redacted.
3. Given operational tasks (db migrate/seed/reset, user/invite/cohort management, import, reports, badge award, token issue), when run via the admin CLI — which is operational tooling (an out-of-band ops interface), not product scope — then they execute the same validated application logic as the API.
4. Given a deployment, when started, then required configuration (connection string, signing key) is validated fail-fast and pending migrations are applied deterministically.
