# L2 — Engagement & Operations (ENGAGE)

Each L2 traces to an L1 in `engagement/L1.md`.

## L2-ENGAGE-001: Session scheduling and calendar
**Traces to:** L1-ENGAGE-001

Staff must schedule sessions/events and view them by cohort in calendar views.

**Acceptance Criteria:**
1. Given the new-session form, when submitted, then title and (for staff) cohort and mentor are required; date, time, location, and optional weekly recurrence are captured.
2. Given recurrence "repeat weekly", when set, then weekly sessions are generated from the start date through the cohort's term-end date (inclusive) per the recurrence rule, and no sessions are generated beyond that date.
3. Given the calendar, when viewed, then month/week/agenda views render events with time, location, mentor, and cohort, filterable by cohort.
4. Given a session, when it exists, then it links to attendance-taking for that session (see L2-ENGAGE-002).

---

## L2-ENGAGE-002: Attendance capture
**Traces to:** L1-ENGAGE-002

Mentors/volunteers must record per-youth attendance with the correct status set, bulk actions, and tallies.

**Acceptance Criteria:**
1. Given a session, when attendance is taken, then each youth can be marked Present, Late, Excused, or Absent (volunteers use a Present/Absent subset), and a running tally and "N of N marked" is shown.
2. Given bulk actions, when "all present"/"clear" is used, then all youth are set accordingly and can then be individually adjusted.
3. Given a per-session note, when added, then it is stored and marked visible to the mentor and director.
4. Given attendance is saved, when confirmed, then attendance is recorded for the session and drives attendance rates and badge streak rules.
5. Given a session already has records, when saved again, then optimistic concurrency prevents lost updates (see L2-NFR-006) and the director can edit on a mentor's behalf.

## L2-ENGAGE-003: Attendance offline capture and sync
**Traces to:** L1-ENGAGE-002

Attendance must be capturable offline and sync on reconnect without loss or duplication.

**Acceptance Criteria:**
1. Given the device is offline, when attendance is marked, then marks are stored locally and a clear offline indicator is shown.
2. Given connectivity returns, when sync runs, then queued attendance is uploaded automatically and merged idempotently (no duplicate records — see L2-NFR-004).
3. Given unsaved attendance changes, when the user tries to leave, then they are warned before losing data (see L2-NFR-007).
4. Given a sync conflict (e.g., director edited the same session), when resolved, then the resolution is deterministic and no record is silently lost.

## L2-ENGAGE-004: Attendance history and rates
**Traces to:** L1-ENGAGE-002

Staff must review attendance by session and by youth with rates and flags.

**Acceptance Criteria:**
1. Given attendance history, when viewed by session, then per-session present counts, rates, and status (saved / needs review / low turnout) are shown.
2. Given attendance history by youth, when viewed, then per-youth attended/late/excused counts, rate, and trend are shown, with below-threshold youth flagged.
3. Given a date range/cohort filter, when applied, then history and rates recompute for that scope.
4. Given export, when requested, then attendance exports as CSV/PDF honouring filters (see L2-REPORT-003).

---

## L2-ENGAGE-005: RSVP to sessions and events
**Traces to:** L1-ENGAGE-003

Youth must RSVP to sessions/events with an optional note and set reminders.

**Acceptance Criteria:**
1. Given a session/event, when a youth RSVPs (going / maybe / can't make it), then the RSVP persists and is visible to the mentor.
2. Given an RSVP with a note, when submitted, then the note is delivered to the mentor.
3. Given "set reminder", when chosen, then a reminder notification is scheduled before the session (see L2-ENGAGE-006).

---

## L2-ENGAGE-006: Announcements composition and targeting
**Traces to:** L1-ENGAGE-004

Staff must compose announcements targeted by audience and role, send now or schedule, and track reads.

**Acceptance Criteria:**
1. Given the compose form, when submitted, then title, message, audience (org/cohort), and role targeting (Youth / Youth+Guardians / Guardians / Mentors / Everyone) are captured.
2. Given "schedule for later", when set with date/time, then the announcement sends at that time; "send now" delivers immediately.
3. Given an announcement is sent, when recipients open it, then per-recipient read state is recorded and an aggregate read rate is shown to staff.
4. Given a recipient, when they view announcements, then only announcements targeted to their audience/role are shown, with unread indicators and mark-all-read.

---

## L2-ENGAGE-007: Messaging
**Traces to:** L1-ENGAGE-005

The system must support 1:1 threaded messaging and mentor group broadcast.

**Acceptance Criteria:**
1. Given a youth and their mentor, when either sends a message, then it is delivered to the thread, timestamped, and the recipient sees an unread indicator and (if connected) near-real-time message delivery (see L2-NFR-005).
2. Given a mentor "broadcast to my group", when sent, then each youth in the cohort receives it as an individual personal message.
3. Given message content, when stored/rendered, then it is sanitized to prevent XSS (see L2-NFR-001) and is only readable by thread participants (and staff per safeguarding policy).
4. Given messaging authorization, when a user attempts to message someone outside their permitted scope, then it is denied (see L2-AUTH-010).

---

## L2-ENGAGE-008: Notifications
**Traces to:** L1-ENGAGE-006

The system must generate a per-user notification feed with deep links and read state.

**Acceptance Criteria:**
1. Given a relevant event (graded work, badge earned, new message, due-soon, session reminder, at-risk alert, approval needed), when it occurs, then a notification is created for the correct user(s) with a title, body, and deep link.
2. Given the notifications feed, when opened, then unread items are distinguished, each links to its target screen, and "mark all read" clears unread state.
3. Given a notification, when created for a connected user, then it is delivered as a near-real-time notification (see L2-NFR-005); otherwise it appears on next load.
4. Given notification generation, when it runs, then it respects the user's notification preferences (see L2-PLATFORM-003).
