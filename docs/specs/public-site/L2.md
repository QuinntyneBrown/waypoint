# L2 — Public Site (PUB)

Each L2 traces to an L1 in `public-site/L1.md`. Acceptance criteria use Given/When/Then.

## L2-PUB-001: Public pages are reachable without authentication
**Traces to:** L1-PUB-001

The public marketing pages must be served to anonymous visitors and must not require or leak authenticated data.

**Acceptance Criteria:**
1. Given an unauthenticated visitor, when they request any public page, then the page renders with HTTP 200 and no sign-in redirect.
2. Given an unauthenticated visitor on a public page, when the page loads, then it exposes no personal data about youth, mentors, or guardians beyond published staff bios/first names.
3. Given a visitor on any public page, when the page renders, then primary calls-to-action to Apply, Sign in, Get involved, and Contact are present and navigate correctly.
4. Given any viewport from XS (<576px) to XL (≥1200px), when a public page renders, then content reflows without horizontal overflow and all tap targets are ≥44px (see L2-NFR-009).

## L2-PUB-002: Landing and program content presents tracks, mentorship, cohorts, and impact
**Traces to:** L1-PUB-001

The landing/about/programs pages must present the two tracks (Bible & Leadership, Coding for Kingdom), the mentorship model, the current cohorts, the 4-step journey, and impact statistics.

**Acceptance Criteria:**
1. Given the programs page, when it renders, then both tracks are described with their modules and outcome badges, and the mentorship model (weekly check-ins, reflection reviews, extra support) is shown.
2. Given the about page, when it renders, then the cohort list shows each cohort's neighbourhood, dates, lead mentor, and status.
3. Given the landing page, when it renders, then the 4-step journey (Apply → Join a cohort → Learn the modules → Lead & graduate) and impact stats are presented.
4. Given content is served, when reviewed, then cohort statuses are sourced from a single authoritative record so the same cohort's status is identical across all public pages.

## L2-PUB-003: Contact, volunteer, and donation requests are captured and acknowledged
**Traces to:** L1-PUB-001

The contact form, volunteer sign-up, and donation flow must validate input, submit, and acknowledge the user; a volunteer request must record the screening-consent acknowledgement.

**Acceptance Criteria:**
1. Given the contact form, when a visitor submits with name, email, topic, and message, then the message is recorded and an acknowledgement is shown; when required fields are missing or email is malformed, then submission is blocked with field-level errors.
2. Given the volunteer form, when a visitor submits, then submission is blocked unless the visitor has acknowledged that volunteers working with youth must complete a screening and reference check.
3. Given the donation flow, when a visitor selects a recurring monthly tier (product decision — confirm with product owner) and confirms, then the request is acknowledged; payment is handled by an external PCI-compliant provider and no card data is stored by the system.
4. Given any public form input, when submitted, then all free-text is validated and sanitized server-side to prevent injection/XSS (see L2-NFR-001).
