# L2 — Multi-Tenancy (TENANCY)

Detailed requirements with acceptance criteria. Each L2 traces to an L1 in `L1.md`.

## L2-TENANCY-001: Every organization-owned record belongs to exactly one organization
**Traces to:** L1-TENANCY-001

Every organization-owned record (people, cohorts, curriculum, submissions, sessions, attendance, messages, notifications, consents, audit entries, settings, applications, and files) must carry a required, immutable organization identifier. Each user account belongs to exactly one organization. Public-site content and Platform Operator accounts are platform-level and belong to no organization.

**Acceptance Criteria:**
1. Given any organization-owned record, when it is created, then it is stamped with the signed-in user's organization server-side and any organization identifier supplied by the client is ignored.
2. Given an existing organization-owned record, when an update attempts to change its organization identifier, then the change is rejected and the record is unchanged.
3. Given an organization-owned record without an organization identifier, when it is persisted, then the database rejects it (non-nullable column with a foreign key to the organization).
4. Given a user account, when it is created by invitation, then it belongs to the organization that issued the invitation and cannot belong to more than one organization.

## L2-TENANCY-002: Every request is scoped to the caller's organization
**Traces to:** L1-TENANCY-001

The server must resolve the caller's organization from their authenticated session (never from a header, query string, route, or body) and must apply it to every read and write of organization-owned data. This is enforced in addition to role scoping (see L2-AUTH-009, L2-AUTH-010).

**Acceptance Criteria:**
1. Given a user in Organization A, when they request any list (people, cohorts, modules, submissions, messages, notifications, reports), then only Organization A's records are returned.
2. Given a user in Organization A who knows the id of a record in Organization B, when they read, update, or delete it, then the response is 404 Not Found (the record's existence is not revealed) and the attempt is written to the audit log (see L2-CONSENT-003).
3. Given a request that supplies an organization id in a header, query string, route, or body, when it is processed, then that value has no effect on which organization's data is accessed.
4. Given a user whose organization is suspended (see L2-TENANCY-005), when they make any authenticated request, then it is rejected with 403 and the "account deactivated" state is shown (see L1-PLATFORM-003).
5. Given search, autocomplete, and uniqueness checks (for example "email already invited"), when evaluated, then they consider only the caller's organization, except that sign-in email addresses remain unique platform-wide.

## L2-TENANCY-003: Background work, exports, and real-time delivery stay inside one organization
**Traces to:** L1-TENANCY-001

Work not started by an HTTP request — scheduled jobs, notification and email dispatch, CSV/PDF exports, bulk import, and near-real-time message delivery — must run under exactly one organization's scope.

**Acceptance Criteria:**
1. Given a scheduled job (for example session reminders or at-risk detection), when it runs, then it processes each organization separately and never combines records from different organizations in one notification, email, or calculation.
2. Given a CSV or PDF export (see L2-REPORT-003), when it is generated, then it contains only the requesting user's organization's records.
3. Given a bulk import, when rows are imported, then every created record belongs to the importing user's organization.
4. Given near-real-time delivery of a notification or message (see L2-NFR-005), when it is pushed, then it reaches only connections of users in the same organization as the recipient.
5. Given an uploaded file, when it is requested by a user in another organization, then the response is 404 Not Found.

## L2-TENANCY-004: Platform Operator provisions an organization
**Traces to:** L1-TENANCY-002

A Platform Operator must be able to create an organization by entering its display name and a unique URL-safe slug, and invite its first Program Administrator by email (see L2-AUTH-003).

**Acceptance Criteria:**
1. Given a Platform Operator on the Organizations screen, when they submit a display name (1–100 characters) and slug (3–40 characters, lowercase letters, digits, and hyphens), then the organization is created in the Active state and appears in the organizations list.
2. Given a slug already used by another organization, when submitted, then the form shows "This slug is already in use" and nothing is created.
3. Given an invalid or empty field, when submitted, then an inline error identifies the field and nothing is created.
4. Given a newly created organization, when the Platform Operator invites a first Program Administrator by email, then an invitation is sent and, once accepted, that user is a Program Administrator of that organization only.
5. Given a user who is not a Platform Operator, when they call any organization-provisioning endpoint, then it is rejected with 403 (see L2-AUTH-009).
6. Given an organization is created or its first administrator invited, when the action completes, then it is recorded in a platform-level audit log with the operator, time, and organization.

## L2-TENANCY-005: Platform Operator suspends and reactivates an organization
**Traces to:** L1-TENANCY-002

A Platform Operator must be able to suspend an organization, which blocks all of its users without deleting any data, and later reactivate it.

**Acceptance Criteria:**
1. Given an Active organization, when the Platform Operator suspends it and confirms in a dialog that names the organization, then its state becomes Suspended and its users' existing sessions are rejected on their next request.
2. Given a Suspended organization, when the Platform Operator reactivates it, then its users can sign in again and all of its data is unchanged.
3. Given a suspended organization, when any of its scheduled jobs would run, then they are skipped and no notifications or emails are sent to its users.
4. Given a suspension or reactivation, when it completes, then it is recorded in the platform-level audit log.

---

## L2-TENANCY-006: Platform Operator cannot access organization data
**Traces to:** L1-TENANCY-002

The Platform Operator role is platform-level. It must see only organization metadata (name, slug, state, created date, number of user accounts) and must not be able to read or change any organization-owned record.

**Acceptance Criteria:**
1. Given a Platform Operator, when they call any organization-owned data endpoint (people, cohorts, curriculum, submissions, messages, reports, consents), then it is rejected with 403.
2. Given a Platform Operator, when they view the organizations list, then each row shows only name, slug, state, created date, and user-account count.
3. Given a Program Administrator, when they attempt any Platform Operator action, then it is rejected with 403.
4. Given the Platform Operator role, when a user is assigned it, then this is possible only through a deployment-time configuration step and never through the application UI.

---

## L2-TENANCY-007: Organizations screen is responsive and accessible
**Traces to:** L1-TENANCY-002

The Platform Operator's Organizations screen must follow the platform's responsive and accessibility rules (see L2-NFR-009, L2-NFR-010).

**Acceptance Criteria:**
1. Given a viewport narrower than 576px, when the Organizations screen is shown, then each organization is presented as a stacked card and there is no horizontal page scroll.
2. Given a viewport of 768px or wider, when the Organizations screen is shown, then organizations are presented as a table with name, slug, state, created date, and user count columns.
3. Given keyboard-only use, when the operator creates, suspends, or reactivates an organization, then every control and dialog is reachable and operable by keyboard with visible focus.
4. Given the organizations list is loading, empty, or fails to load, when shown, then the loading, empty ("No organizations yet"), and error states with a retry action are displayed.

---

## L2-TENANCY-008: Tenant scoping does not degrade performance
**Traces to:** L1-TENANCY-001

Adding organization scoping must not measurably slow the product.

**Acceptance Criteria:**
1. Given the existing performance suite (see L2-NFR-008), when run against a database holding 50 organizations, then every measured endpoint stays within its existing p95 latency budget.
2. Given any index on an organization-owned table used for lookup, when defined, then it leads with the organization identifier.

---

## L2-TENANCY-009: Existing data is migrated into a default organization
**Traces to:** L1-TENANCY-003

When multi-tenancy is deployed, all pre-existing data must be assigned to one default organization whose display name and logo are taken from the current organization settings (see L1-ADMIN-004).

**Acceptance Criteria:**
1. Given a database containing pre-tenancy data, when the migration runs, then one default organization is created and every organization-owned record and user account is assigned to it.
2. Given the migration has run, when the row counts of every organization-owned table are compared with the pre-migration counts, then they are identical.
3. Given an existing user, when they sign in after the migration, then they see exactly the same data and screens as before.
4. Given the migration fails part-way, when it stops, then all of its changes are rolled back and the database is left in its pre-migration state.
5. Given the migration has already run, when it is run again, then it makes no changes.
