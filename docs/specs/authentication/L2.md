# L2 — Authentication & Access (AUTH)

Each L2 traces to an L1 in `authentication/L1.md`.

## L2-AUTH-001: Email/password sign-in
**Traces to:** L1-AUTH-001

The system must authenticate by email + password and issue an access token plus a rotating refresh token on success.

**Acceptance Criteria:**
1. Given valid credentials, when a user signs in, then an access token and refresh token are issued, the user is routed to their role's home surface, and the sign-in is audit-logged (see L2-CONSENT-003).
2. Given an unrecognized email, when sign-in is attempted, then the response is a generic authentication failure that does not confirm whether the email exists.
3. Given a recognized email with a wrong password, when sign-in is attempted, then it fails and the failed-attempt counter for that account increments (see L2-AUTH-006).
4. Given "remember me" is unchecked, when the browser session ends, then the session is not silently restored; given it is checked, then a longer-lived session is allowed as a deliberate product decision but the user is warned it is not recommended on shared devices (confirm with product owner).
5. Given the sign-in endpoint, when called repeatedly, then it is rate-limited to mitigate credential stuffing (see L2-NFR-002).

## L2-AUTH-003: Invitation issuance
**Traces to:** L1-AUTH-003

Staff must be able to create role-scoped invitations (single or bulk) delivered by email, optionally scoped to a cohort and mentor, with a defined expiry.

**Acceptance Criteria:**
1. Given a Program Administrator (or a mentor issuing a youth invite), when they create an invitation with an email and role, then an invitation is recorded with status "Pending" and a unique tokenized link is emailed.
2. Given a bulk invite with multiple email addresses and one role, when submitted, then one Pending invitation is created per address and the count is reported.
3. Given an invitation is created, when persisted, then it expires 14 days after issuance (confirm with product owner), and this expiry duration is applied consistently to every invitation.
4. Given only authorized roles per the permission matrix, when a non-authorized user attempts to invite, then the action is denied (403 — see L2-AUTH-009).

## L2-AUTH-004: Invitation acceptance, resend, and revoke
**Traces to:** L1-AUTH-003

An invitee must accept by setting display name + password; staff must be able to resend and revoke invitations; expired/revoked links must not work.

**Acceptance Criteria:**
1. Given a valid, unexpired invitation link, when the invitee sets a display name and a policy-compliant password and agrees to community guidelines, then their account is activated with the role/cohort/mentor from the invitation and they proceed to onboarding.
2. Given an expired invitation link, when opened, then acceptance is blocked and the user is shown the invite-expired state with a "request a new invite" path (see L2-PLATFORM-011).
3. Given a Pending invitation, when staff resend it, then a fresh link/expiry is issued; when staff revoke it, then the link stops working immediately and status becomes "Revoked".
4. Given an accepted invitation, when the same link is reused, then it is rejected (single-use).
5. Given invitation tokens, when generated, then they are cryptographically random and stored hashed at rest.

## L2-AUTH-005: Password reset
**Traces to:** L1-AUTH-004

Users must be able to request a reset link and set a new password without the system disclosing account existence.

**Acceptance Criteria:**
1. Given any submitted email on "forgot password", when processed, then the response and UI are identical whether or not the email exists (no enumeration), and a reset link is emailed only if it exists.
2. Given the reset-link-sent confirmation, when shown, then the email address is masked and a resend option is available.
3. Given a valid reset link, when the user sets a new password meeting policy (see L2-AUTH-008), then the password is updated, existing sessions/refresh tokens are invalidated, and success is confirmed.
4. Given an expired or already-used reset link, when opened, then it is rejected with a clear message.
5. Given the reset form, when the two password fields differ, then submission is blocked with an error.

## L2-AUTH-006: Account lockout
**Traces to:** L1-AUTH-005

After too many failed attempts, the account must lock for a defined duration and offer recovery.

**Acceptance Criteria:**
1. Given consecutive failed sign-in attempts reaching the configured threshold, when the next attempt occurs, then the account is locked and the user is shown the account-locked state stating the lock duration (default 15 minutes).
2. Given a locked account, when the lock duration elapses, then sign-in is permitted again without manual intervention.
3. Given a locked account, when locked, then password-reset and contact-mentor recovery paths remain available.
4. Given a lockout occurs, when it triggers, then the event is logged for security monitoring.

---

## L2-AUTH-007: Shared-device sign-out and session expiry
**Traces to:** L1-AUTH-006

The system must fully tear down sessions on sign-out and expire idle sessions while preserving drafts.

**Acceptance Criteria:**
1. Given a signed-in user on a shared device, when they sign out, then all tokens for that session are revoked and no account data remains accessible on the device without re-authentication.
2. Given an idle authenticated session, when the inactivity timeout elapses, then the user is signed out and shown the session-expired state, and any in-progress draft (e.g., a reflection) is preserved for recovery (see L2-PLATFORM-010).

---

## L2-AUTH-008: Password policy and hashing
**Traces to:** L1-AUTH-009

All passwords must satisfy a defined policy and be stored using a strong adaptive hash.

**Acceptance Criteria:**
1. Given any password set (invite-accept, reset, change), when submitted, then it must contain at least 8 characters including at least one letter and at least one number (confirm with product owner), and this policy is enforced identically everywhere.
2. Given a password is stored, when persisted, then it is hashed with a strong adaptive algorithm (e.g., bcrypt) with a per-user salt; plaintext is never stored or logged.
3. Given a password field, when displayed, then a show/hide toggle is available and the field is excluded from analytics/telemetry capture.

---

## L2-AUTH-009: Authorization is enforced server-side on every protected action
**Traces to:** L1-AUTH-007

Every non-public endpoint must verify authentication and role/resource authorization server-side; client-side gating is never sufficient.

**Acceptance Criteria:**
1. Given an unauthenticated request to a protected endpoint, when received, then it is rejected with 401.
2. Given an authenticated user whose role lacks permission for an action, when they attempt it, then it is rejected with 403 and the attempt is logged (see L2-CONSENT-003).
3. Given a mentor requesting data for a youth not assigned to them, when the request is made, then it is denied even if the youth's id is known (no IDOR).
4. Given a youth requesting another youth's data, when the request is made, then it is denied.
5. Given the canonical system role set — Youth, Mentor, Program Administrator, Guardian, Volunteer, and Public (Public meaning unauthenticated visitors, who may access public information only) — and noting that "Lead Mentor" is a per-cohort designation rather than a system role, the server must enforce the following permission matrix exactly on every protected action:

| Action | Youth | Mentor | Program Administrator | Guardian | Volunteer | Public |
| --- | --- | --- | --- | --- | --- | --- |
| Manage users & roles | No | No | Yes | No | No | No |
| Approve applications | No | No | Yes | No | No | No |
| Edit curriculum | No | No | Yes | No | No | No |
| Record attendance | No | Assigned cohorts only | Yes | No | Assigned sessions only | No |
| View youth progress | Own records only | Assigned youth only | All cohorts | Own child's shared aggregate only | No | No |
| Give guardian consent | No | No | No | Own child only | No | No |
| Export / import data | No | No | Yes | No | No | No |

## L2-AUTH-010: Role-scoped data visibility
**Traces to:** L1-AUTH-007

Each role must see only the data its scope permits, per the role scopes defined by the PRD (see L2-AUTH-009).

**Acceptance Criteria:**
1. Given a mentor, when they load rosters/dashboards, then only their assigned youth/cohorts are returned.
2. Given a guardian, when they load the portal, then only their own child's shared aggregate data is returned and never lesson content, quiz answers, private reflections, or account fields.
3. Given a volunteer, when they load their portal, then only their assigned session, their own schedule, and a names-only attendance roster with Present/Absent state are returned; at-risk flags, hours, youth progress, grades, records, and messaging are not accessible (see L2-VOLUNTEER-001).
4. Given a youth, when they load any screen, then only their own records are returned.
5. Given a Program Administrator, when they load org data, then all cohorts are visible, but private check-in note contents remain restricted (see L2-MENTOR-006, L2-CONSENT-003).

## L2-AUTH-011: Youth onboarding wizard
**Traces to:** L1-AUTH-008

A newly activated youth must be guided through onboarding with the ability to skip.

**Acceptance Criteria:**
1. Given a first sign-in after invite acceptance, when onboarding starts, then the youth can set display name and pronouns and optionally add a photo.
2. Given onboarding, when the cohort step is shown, then the pre-assigned cohort and mentor are confirmed (read-only, not chosen by the youth).
3. Given onboarding, when the notifications step is shown, then default preferences are applied (lesson reminders on, mentor messages on, announcements off) and can be adjusted (see L2-PLATFORM-003).
4. Given onboarding, when the youth chooses "skip for now", then they land on youth home and onboarding can be resumed later.

---

## L2-AUTH-012: Token security and session management
**Traces to:** L1-AUTH-009

Access/refresh tokens must be issued, stored, and rotated securely.

**Acceptance Criteria:**
1. Given sign-in, when tokens are issued, then the access token is short-lived (~60 min) and the refresh token is long-lived, rotating, and stored hashed at rest.
2. Given a refresh token is reused after rotation, when detected, then the whole token family is revoked (reuse detection) and the user must re-authenticate.
3. Given sign-out or password change, when it occurs, then associated refresh tokens are revoked.
4. Given tokens in transit, when transmitted, then only over HTTPS; production rejects non-TLS and sets security headers (see L2-NFR-002).
