# L2 — Consent & Safeguarding (CONSENT)

Each L2 traces to an L1 in `consent-and-safeguarding/L1.md`.

## L2-CONSENT-001: Guardian consent capture with e-signature
**Traces to:** L1-CONSENT-001

The system must capture guardian participation consent (required) and media/photo consent (optional, granular) with a typed e-signature record.

**Acceptance Criteria:**
1. Given a guardian consent form for a specific youth, when submitted, then guardian full name, relationship, participation-consent checkbox, and a typed signature are required; media/photo consent is optional.
2. Given media consent, when granted, then granular sub-options (all photos/video, group-only, first-name-in-captions) are recorded independently.
3. Given consent is recorded, when saved, then the system stores signer name, method (typed e-signature), timestamp/date, a unique reference id, and a validity window, and emails a copy of the record to the guardian.
4. Given recorded consent, when a guardian withdraws it, then the withdrawal is recorded and downstream permissions (e.g., media use) are revoked going forward.
5. Given the org policy requires re-consent each new term, when a new term begins, then prior-term consent does not satisfy the new term and re-consent is required (see L2-ADMIN-006).

## L2-CONSENT-002: Consent gating for minors
**Traces to:** L1-CONSENT-001

A minor without participation consent must be blocked from program participation and routed to obtain consent.

**Acceptance Criteria:**
1. Given a minor youth without participation consent, when they sign in, then they are held on the consent-required state and cannot access lessons/quizzes/submissions (see L2-PLATFORM-011).
2. Given the consent-required state, when the youth chooses "notify my guardian", then a secure consent-request link is sent to the guardian's provided email/phone.
3. Given a guardian completes participation consent, when recorded, then the minor's access is unblocked without further manual steps.
4. Given a youth flagged "Needs consent" in admin/import views, when consent is later recorded, then their status clears automatically.
5. Given consent status, when checked, then it is evaluated server-side on each protected youth action (not only at sign-in).

## L2-CONSENT-003: Audit log of security- and safeguarding-relevant actions
**Traces to:** L1-CONSENT-002

The system must record an append-only audit trail with actor, action, target entity, timestamp, and source.

**Acceptance Criteria:**
1. Given any mutating administrative or safeguarding action (approve application, change role, edit lesson, take attendance, log check-in, award badge, sign in, deactivate account), when it occurs, then an audit entry is written with who/action/target/when/source (device + location).
2. Given the audit log view, when a check-in entry is shown, then the private note content is not exposed (marked private/redacted).
3. Given audit entries, when stored, then they are append-only/tamper-evident and cannot be edited or deleted through the application.
4. Given the audit log, when accessed, then only Program Administrators may view it, it is filterable by user/action/date, and it is paginated.
5. Given an export of the audit log, when requested, then it is available as CSV and the export itself is audit-logged.

## L2-CONSENT-004: Minor-specific safeguarding controls
**Traces to:** L1-CONSENT-003

Because the platform serves minors, safeguarding controls must be enforced beyond generic PII rules.

**Acceptance Criteria:**
1. Given a youth is a minor, when any participation begins, then guardian participation consent must be present (see L2-CONSENT-002).
2. Given mentor–youth contact records (messages, check-ins), when stored, then they are retained for safeguarding accountability and visible to the director per policy.
3. Given media of a youth, when used anywhere, then it is permitted only where media consent (with the applicable granular option) is on record and not withdrawn.
4. Given a volunteer/mentor account, when created, then role assignment does not by itself grant youth-record access beyond the role's defined scope (see L2-AUTH-010).
