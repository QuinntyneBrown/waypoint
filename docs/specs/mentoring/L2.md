# L2 — Mentoring & Coaching (MENTOR)

Each L2 traces to an L1 in `mentoring/L1.md`.

## L2-MENTOR-001: Mentor dashboard and roster
**Traces to:** L1-MENTOR-001

Mentors must see a scoped dashboard and roster of their youth.

**Acceptance Criteria:**
1. Given a signed-in mentor, when the dashboard loads, then it shows counts for their youth, pending reviews (with overdue indicators), average progress, and at-risk youth — computed only over their assigned youth.
2. Given the roster, when searched/filtered (all/on-track/at-risk/new), then results narrow accordingly with a labelled empty state.
3. Given the reviews queue preview, when shown, then each item indicates youth, item type, and due/overdue status and links to grading.
4. Given a mentor requests any roster data, when served, then it excludes youth not assigned to them (see L2-AUTH-010).

---

## L2-MENTOR-002: Youth detail record (mentor)
**Traces to:** L1-MENTOR-002

Mentors must access a full per-youth record with coaching actions.

**Acceptance Criteria:**
1. Given an assigned youth, when the detail loads, then profile, guardian contact, progress, attendance, check-in history, submissions, and competencies are available in tabs.
2. Given an at-risk youth, when viewed, then an at-risk banner shows the reason and who flagged it and when.
3. Given a non-assigned youth id, when a mentor requests the record, then it is denied with 403 (see L2-AUTH-009).
4. Given guardian contact is shown, when displayed, then it is available to the assigned mentor and staff only.

---

## L2-MENTOR-003: Submission grading with rubric and outcomes
**Traces to:** L1-MENTOR-003

Mentors must grade submissions against the rubric and approve, request revision, or save a draft.

**Acceptance Criteria:**
1. Given a pending submission, when graded, then the mentor can score each rubric criterion within its point range and the total is computed.
2. Given the mentor approves, when confirmed, then the submission becomes Approved, rubric points/badge (if any) are applied, and the youth is notified via near-real-time notification delivery.
3. Given the mentor requests a revision, when confirmed, then a note is mandatory, guardian notification is optional (default on), the submission becomes Needs revision, and the youth may resubmit.
4. Given a draft grade, when saved, then it is retained without changing the youth-visible status.
5. Given grading actions, when performed, then they are restricted to the assigned mentor/staff and are audit-logged (see L2-CONSENT-003).

---

## L2-MENTOR-004: Quiz assessment approval and override
**Traces to:** L1-MENTOR-004

Mentors must approve or override auto-scored quizzes before they count; youth see only approved scores.

**Acceptance Criteria:**
1. Given an auto-scored quiz, when the mentor reviews it, then they can approve the auto-score or enter an override within the valid range.
2. Given approval, when confirmed, then the approved score is what counts toward progress/averages and is the only score the youth sees (see L2-LEARN-005).
3. Given "approve all", when invoked, then all pending assessments in scope are approved in one action and each is recorded.
4. Given an override, when applied, then both the auto-score and the override are retained for audit, and the change is audit-logged (see L2-CONSENT-003).

## L2-MENTOR-005: Competency assessment
**Traces to:** L1-MENTOR-005

Mentors must set competency levels per youth with notes.

**Acceptance Criteria:**
1. Given the competency tracker for a youth, when a competency level is set (Not started → Developing → Proficient → Mastered), then it persists with the assessing mentor and timestamp.
2. Given notes per competency, when saved, then they persist and a summary count (e.g., "mastered or proficient") updates.
3. Given saved assessments, when the youth's progress view or a report renders competencies, then it reflects the latest assessment (see L2-LEARN-010).

---

## L2-MENTOR-006: Check-ins
**Traces to:** L1-MENTOR-006

Mentors must log check-ins with visibility controls and view a history.

**Acceptance Criteria:**
1. Given the check-in form, when saved, then youth, date, and type are required, and engagement/mood, goals, prayer requests, action items, and next follow-up date are captured.
2. Given the sharing toggle, when off (default), then the check-in is a private mentor note; when on, then it is visible on the youth's progress page (and to guardian where applicable).
3. Given prayer requests, when stored, then they remain mentor-only unless sharing is explicitly enabled — even when other check-in fields are shared.
4. Given "guardian was informed" is set, when saved, then it is recorded on the check-in.
5. Given the check-in history, when loaded, then entries show type, date, visibility, and follow-up, filterable by youth and type; private content is not exposed to unauthorized roles (see L2-AUTH-010, L2-CONSENT-003).

## L2-MENTOR-007: At-risk flags
**Traces to:** L1-MENTOR-007

The system must surface at-risk signals and let mentors raise/resolve flags visible to the director.

**Acceptance Criteria:**
1. Given a youth's activity, when any of the default at-risk thresholds is met — 7 or more days inactive, OR 1 or more missed sessions, OR progress more than 15% below the cohort average — then the youth appears in the at-risk list with the specific reason(s) that triggered the flag. Each threshold is a configurable key (confirm with product owner).
2. Given a flagged youth, when the mentor takes action, then they can message, log a check-in, or unflag.
3. Given unflagging, when confirmed, then a resolution reason (Reconnected / Handed to director / Left program / Flagged in error) is captured and the youth leaves the at-risk list; re-flagging is possible if signals recur.
4. Given a flag is raised/resolved, when it occurs, then it is visible to the director and audit-logged (see L2-CONSENT-003).

---

## L2-MENTOR-008: Assign work to youth or cohort
**Traces to:** L1-MENTOR-008

Mentors must assign lessons/modules/projects to individuals or a whole cohort with due date, reminder, and message.

**Acceptance Criteria:**
1. Given the assign-work form, when submitted, then a type and item are required, and recipients are either selected individuals or the whole cohort.
2. Given a due date and reminder cadence, when set, then they are stored and drive reminders/notifications (see L2-ENGAGE-008).
3. Given an optional message, when included, then each recipient receives it as an in-app message alongside the assignment.
4. Given confirmation, when the mentor confirms, then AssignedWork records are created for each recipient and appear in their journeys, and the count is reported.
