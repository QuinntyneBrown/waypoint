# L2 — Program Administration (ADMIN)

Each L2 traces to an L1 in `program-administration/L1.md`.

## L2-ADMIN-001: People directory with search and filters
**Traces to:** L1-ADMIN-001

Admins must be able to list, search, and filter all people by role, cohort, and free text.

**Acceptance Criteria:**
1. Given the people directory, when loaded, then it lists people with role, cohort, mentor, status, and last-active, paginated.
2. Given filters (role, cohort) and a search term, when applied, then results narrow accordingly and an empty result shows an empty state with an invite CTA.
3. Given a large directory, when queried, then results return within the performance budget (see L2-NFR-008) using server-side paging.
4. Given any viewport, when the table renders on XS screens, then rows reflow to card layout with labelled fields (no horizontal page overflow — see L2-NFR-009).

## L2-ADMIN-002: Person record and account lifecycle
**Traces to:** L1-ADMIN-001

Each person must have a detail record supporting edit, role change, password reset, deactivate, and remove, with correct data-retention semantics.

**Acceptance Criteria:**
1. Given a youth record, when viewed, then it shows profile, guardian contact + consent status, progress, attendance, notes, and account tabs.
2. Given an admin deactivates an account, when confirmed, then the user is signed out and cannot sign in, but their progress and records are retained; deactivation is reversible.
3. Given an admin removes a person, when confirmed, then their access is revoked and they are removed from active use, but progress records are retained for reporting; removal is irreversible and requires explicit confirmation.
4. Given a role change to a staff role, when initiated, then the UI warns it grants access to other youth's records and the change takes effect immediately on confirmation and is audit-logged (see L2-CONSENT-003).
5. Given "send password reset" from a person record, when triggered, then a reset link is emailed to that user and the action is audit-logged.

## L2-ADMIN-003: Cohort creation and management
**Traces to:** L1-ADMIN-002

Admins must create and edit cohorts and manage their membership.

**Acceptance Criteria:**
1. Given the new-cohort form, when submitted, then cohort name, track, and lead mentor are required; start date, end date, and meeting location are captured.
2. Given a cohort detail, when an admin adds youth, then selected existing youth are enrolled (or an invite path is offered), and membership counts update.
3. Given a cohort, when edited, then name, lead mentor, and location can be updated and changes are audit-logged.
4. Given cohort list/detail data loads fail, when they error, then an error state with retry is shown; when empty, then an empty state is shown.

## L2-ADMIN-004: Org-wide progress board (spreadsheet replacement)
**Traces to:** L1-ADMIN-002

The system must present a per-youth × per-module progress matrix per cohort/track with cell states and aggregate rows.

**Acceptance Criteria:**
1. Given a cohort and track selection, when the progress board loads, then each youth row shows per-module cell state (Done / In progress / Not started / Not assigned), quiz average, and overall %, plus a cohort-average footer row.
2. Given the matrix on a narrow viewport, when rendered, then it is horizontally scrollable within its own container without causing page-level horizontal overflow (see L2-NFR-009).
3. Given the progress board, when the user exports it, then CSV/PDF export honours the current cohort/track selection (see L2-REPORT-003).
4. Given underlying progress changes in real time, when a value updates, then the board reflects it via a live update or on next refresh (see L2-NFR-005).

## L2-ADMIN-005: Mentor–youth and mentor–cohort assignment
**Traces to:** L1-ADMIN-003

Admins must assign mentors to youth and cohorts and see caseloads and imbalance.

**Acceptance Criteria:**
1. Given the assign-mentors tool, when an admin pairs a youth with a mentor, then the youth's assigned mentor updates and appears on the mentor's roster immediately.
2. Given a cohort, when a lead mentor and supporting mentors are set, then a mentor may hold different roles across cohorts (lead in one, supporting in another).
3. Given mentor caseloads, when the staff report loads, then per-mentor youth counts, check-ins, and reviews are shown with a load-balance indicator against the target band, and overload is flagged (see L2-REPORT-001).

## L2-ADMIN-006: Organization settings
**Traces to:** L1-ADMIN-004

The director must configure org identity, terms, tracks, and consent policy.

**Acceptance Criteria:**
1. Given org general settings, when saved, then the organization name, display name, logo, city, and contact email persist (the contact email is shown to guardians on consent forms and receipts). The colour palette is fixed platform-wide and cannot be changed per organization.
2. Given terms/cohort cycles, when managed, then terms with date ranges and status are maintained.
3. Given track enable/disable, when a track is turned off, then existing youth progress is retained but new assignments in that track are paused.
4. Given consent settings, when saved, then the consent statement text, "require re-consent each term", and "require photo/media consent" persist and drive consent flows (see L2-CONSENT-001, L2-CONSENT-002).
5. Given org settings, when changed, then only a Program Administrator may change them (see L2-AUTH-009) and changes are audit-logged (see L2-CONSENT-003).
