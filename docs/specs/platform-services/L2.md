# L2 — Platform Services (PLATFORM)

Each L2 traces to an L1 in `platform-services/L1.md`.

## L2-PLATFORM-002: Profile settings
**Traces to:** L1-PLATFORM-002

Users must manage profile details, photo, and password.

**Acceptance Criteria:**
1. Given profile settings, when saved, then first/last name and email are required and validated; email format is enforced.
2. Given a managed field (e.g., youth cohort managed by mentor), when displayed, then it is read-only to the user.
3. Given a profile photo upload, when selected, then type and size are validated (JPG/PNG ≤ configured max) and stored safely (see L2-NFR-001).
4. Given "change password", when submitted, then current password is verified, the new password meets policy (see L2-AUTH-008), and confirmation must match; on success other sessions are invalidated.

---

## L2-PLATFORM-003: Notification preferences
**Traces to:** L1-PLATFORM-002

Users must configure per-event notification preferences, delivered as in-app notifications with email as an optional channel.

**Acceptance Criteria:**
1. Given notification settings, when saved, then per-event toggles persist for in-app notifications and for the optional email channel (e.g., new lesson, work graded, new message, reminders).
2. Given a user has disabled a channel for an event, when that event occurs, then no notification is sent on that channel for that user (see L2-ENGAGE-008).

---

## L2-PLATFORM-004: Display & accessibility preferences
**Traces to:** L1-PLATFORM-002

Users must set text size, high contrast, reduced motion, underline links, and reading font.

**Acceptance Criteria:**
1. Given display settings, when text size is changed, then a live preview updates and the preference persists and applies across the app.
2. Given accessibility toggles (high contrast, reduce motion, underline links), when enabled, then the UI honours them app-wide.
3. Given reduced motion is on, when transitions/animations would play, then they are disabled or minimized (see L2-NFR-010).
4. Given a reading-font selection, when set, then UI chrome reflects it.

---

## L2-PLATFORM-005: Help and support
**Traces to:** L1-PLATFORM-002

Users must access self-serve help and submit support requests.

**Acceptance Criteria:**
1. Given the help center, when opened, then FAQ/topic content is browsable and role-appropriate.
2. Given the support form, when submitted, then category and description are required; an optional screenshot upload is validated (PNG/JPG ≤ configured max — see L2-NFR-001); a reply-to email is captured.
3. Given a support request is submitted, then it is persisted and emailed to the program support inbox (the director), and the user receives an on-screen acknowledgement that their request was received.

---

## L2-PLATFORM-006: Forbidden (403) handling
**Traces to:** L1-PLATFORM-003

Unauthorized access must yield a clear 403 with recovery.

**Acceptance Criteria:**
1. Given a user accesses an area their role forbids, when denied, then a 403 state explains the role mismatch and offers "switch account" and "back to your home".
2. Given the 403 is shown, when rendered, then no data from the forbidden resource is leaked.

---

## L2-PLATFORM-007: Not found (404) handling
**Traces to:** L1-PLATFORM-003

Missing pages/resources must yield a 404 with navigation back.

**Acceptance Criteria:**
1. Given a broken/moved link or missing resource, when requested, then a 404 state is shown with a path back to a safe home/sitemap.

---

## L2-PLATFORM-008: Server error (500) handling
**Traces to:** L1-PLATFORM-003

Server errors must be handled gracefully without data loss or leakage.

**Acceptance Criteria:**
1. Given an unhandled server error, when it occurs, then the user sees a friendly 500 state with retry, no stack trace or internal detail is exposed, and the error is logged/alerted server-side (see L2-NFR-011).
2. Given a 500 during a data action, when it occurs, then the user's in-progress work is preserved where possible.

---

## L2-PLATFORM-009: Maintenance (503) handling
**Traces to:** L1-PLATFORM-003

Planned maintenance must present a 503 state.

**Acceptance Criteria:**
1. Given maintenance mode, when a user visits, then a 503 maintenance state is shown with a "check again" action and reassurance that nothing is lost.
2. Given maintenance mode is active, when API calls are made, then they return 503 with a Retry-After indication.

---

## L2-PLATFORM-010: Session-expired and account-deactivated handling
**Traces to:** L1-PLATFORM-003

Expired sessions and deactivated accounts must present appropriate states.

**Acceptance Criteria:**
1. Given a session expires from inactivity, when the user acts, then a session-expired state is shown, drafts are preserved, and re-sign-in is offered (see L2-AUTH-007).
2. Given a deactivated account signs in, when attempted, then an account-inactive state is shown with a path to contact the director; sign-in is refused.

---

## L2-PLATFORM-011: Consent-required, invite-expired, and no-cohort handling
**Traces to:** L1-PLATFORM-003

Youth-lifecycle gates must present clear states and recovery.

**Acceptance Criteria:**
1. Given a minor without consent, when they sign in, then the consent-required state is shown with a "notify my guardian" flow and an immediate guardian-sign path (see L2-CONSENT-002).
2. Given an expired invite link, when opened, then the invite-expired state is shown with a "request a new invite" flow to the inviter (see L2-AUTH-004).
3. Given an authenticated youth not yet placed in a cohort, when they sign in, then the no-cohort state is shown with a message-your-mentor path, and program content stays locked until placement.

---

## L2-PLATFORM-012: Offline state and queued-sync visibility
**Traces to:** L1-PLATFORM-003

Offline conditions must be clearly indicated with queued-change visibility.

**Acceptance Criteria:**
1. Given no connectivity, when the app detects it, then an offline banner/state is shown and read-only content already loaded remains usable.
2. Given queued writes exist offline, when shown, then the count/summary of pending changes is visible.
3. Given connectivity returns, when detected, then the offline indicator clears.
